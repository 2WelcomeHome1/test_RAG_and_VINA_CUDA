# Отчёт по тестовому заданию: RAG API

## Запуск

Нужен Docker с Compose v2. Порт 8000 на хосте должен быть свободен (иначе задайте другой в `RAG_API_PORT` в `.env`).

```sh
cp .env.example .env
docker compose up --build -d --wait      # дождаться, пока все сервисы станут healthy
docker compose exec -T rag-api pytest -q                          # ожидается: 43 passed
docker compose exec -T rag-api python -m scripts.mutation_check   # ожидается: 50/50 killed, ~1.5 мин
```

Ручная проверка:

```sh
curl -F "file=@document.pdf" localhost:8000/v1/documents
curl -H 'Content-Type: application/json' -d '{"query": "ваш вопрос"}' localhost:8000/v1/query
```

- Swagger UI: <http://localhost:8000/docs>
- Консоль MinIO: <http://localhost:19001> (`minioadmin` / `minioadmin`)
- Тесты работают с отдельной базой `rag_test` и бакетом `rag-documents-test`, рабочие данные не трогают.

Остановка: `docker compose down` (данные сохраняются) или `docker compose down -v` (с удалением данных).

## Что сделано

**Соответствие заданию**
- Образ MinIO заменён на тот же релиз из `bitnamilegacy`, стек запускается с нуля.
- Схема БД вынесена в миграции `migrations/*.sql`, тест проверяет их на пустой базе.
- API доступен на порту 8000; у всех сервисов healthcheck и автоперезапуск.
- `EMBEDDING_PROVIDER` / `ANSWER_PROVIDER` действительно выбирают провайдера.
- README: запуск, риск сбоя между S3 и commit, Mermaid-схема корпоративного контура, план из 3 улучшений, таблица «тест → мутант».

**Исправленные баги**
- XLSX с пустыми ячейками и PPTX с таблицами и группами фигур отклонялись как повреждённые.
- Для Markdown и DOCX в месте источника не указывался раздел.
- Загрузки шли последовательно, тест на параллельность этого не видел; теперь проверяется барьером.
- `pytest` стирал рабочие данные; теперь у тестов отдельное хранилище.

**Аудит устойчивости и производительности** (все находки подтверждены замерами)
- Файл из коротких строк: было +3 ГБ памяти на 0.4 МБ файла (5 МБ ронял API) → упаковка чанков, 115 МБ на 5 МБ.
- Zip-бомба DOCX: было 645 МБ памяти и 250 с CPU → отказ `422` до разбора.
- Тысячи одинаковых чанков ломали поиск HNSW → повторы хранятся один раз.
- Нет таймаутов на S3/БД (зависание минутами) → ограниченные таймауты, `503`/`500` за секунды.
- Пул соединений к БД с быстрым восстановлением после её перезапуска.
- Повреждённая страница/слайд/лист пропускается с предупреждением `warnings`, остальное индексируется.
- При обрыве во время COMMIT оригинал в S3 не удаляется.
- Логирование сбоев и «осиротевших» файлов; JSON-ответ на любую непредвиденную ошибку.
- PDF с AES без пароля на открытие загружаются; запрос `???` не возвращает случайные цитаты.
- Контейнер не от root, версии всех зависимостей закреплены (`constraints.txt`).
- Код разделён на модули `main` / `extraction` / `providers` / `storage`, эндпоинты зависят от интерфейсов провайдеров.

**Итог:** тестов было 22, стало **43**; мутантов было 24, стало **50**, выживших нет.

## Что оставлено в плане

| Пункт | Суть |
|---|---|
| 1. Смысловой поиск и LLM | Многоязычная модель, порог релевантности, генерация ответа со ссылками, метрики качества |

**Сознательно не делали**
- **Celery:** `202` сломал бы контракт, а брокер добавил бы проблему рассинхрона с БД. Очередь в PostgreSQL ставит задачу в одной транзакции с документом.
- **Метрики и JSON-логи:** зависят от стека мониторинга заказчика, описаны в README.

## Известные ограничения

- Поиск лексический, порога релевантности нет (следствие детерминированных провайдеров).
- «Осиротевший» файл в S3, если процесс погибнет между загрузкой и commit.
- Разбор файлов в процессе API: худший допустимый DOCX — около 15 с CPU.
- Одинаковые фрагменты из разных документов не дедуплицируются.
- Образ MinIO из замороженного репозитория `bitnamilegacy`.
